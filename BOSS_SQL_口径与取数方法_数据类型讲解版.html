取数总原则：不要先找表，先回答四个口径问题

1. 业务对象

是订单、用户、流量、券、积分、AARR触达、价格，还是抖音链路？不同对象对应不同事实表。

2. 分析口径

是否需要Comp、是否剔EC、是否剔黑产、是否按APP/WMP/AMP/3PO拆分？

3. 时间窗口

同比、MTD、QTD、Rolling 90D、T+30/T+90留存窗口，不同写法会直接改变结果。

4. 输出指标

Sales、GC、User、Freq、AC、DAU、Order UV、Redeem、Retention等不能混用分母。

优先级建议：全量口径以v2.0为主；其中new_01/new_02是APP PMIX一级/二级分类的最新权威；重复口径按编号更小的文件为准，编号越小代表查询越新。

Sales / GC / User / Freq / AC：OC分渠道生意怎么取

适用问题：APP/WMP/AMP各渠道Sales、GC、User、Freq、AC的同比、MTD、QTD、Comp表现，以及FC-/MDS/EC拆分。

1.1 首选底表与口径

用途首选表关键字段备注
品类/券/渠道拆分Saleshive.dws_order.t_order_pmix_for_analysis_dorder_channel, be_type, top_receive_channel, top_net_amount, is_gc_count, item_pmix_typetop-item级pmix宽表，是品类/券归因/渠道拆分主力表。
订单主事实/NRE/留存hive.ads_order.t_order_apply_dmid, order_id, is_gc_count, order_net_amount, order_channel, order_type, is_new_customer适合用户分层、GC、留存、渠道行为分析。
OC正式分渠道月报pmix表 + comp flag + calendaris_comp_monthly, date mapping正式口径使用官方月comp flag和日历映射去年同自然日。

1.2 通用公式

GC = COUNT(DISTINCT order_id) WHERE is_gc_count = 1 Freq = GC ÷ COUNT(DISTINCT mid) AC = SUM(Sales) ÷ SUM(GC) Sales字段：pmix表 top_net_amount；订单表 order_net_amount
注意：AC是Sales/GC，人均销售是Sales/Usercount，两者不能混用。

1.3 渠道与FC-/MDS/EC拆分

渠道/归因判定条件使用场景
APPorder_channel = 'New APP'APP channel生意。
WMPorder_channel = 'Wechat MP'微信小程序生意。
AMPorder_channel = 'AliPay MP'支付宝小程序生意。
3POorder_type='MDS' AND order_channel IN ('MeiTuan','Eleme','JD')分析层3PO通常含JD；但ej_order_ana底表is_3po不含JD，复用需对齐。
FC-order_channel='New APP' AND be_type<>'MDS' AND top_receive_channel NOT IN EC八渠道堂食剔EC APP生意。
ECtop_receive_channel IN EC八渠道，或订单级is_ec_order=1受券渠道/电商归因。

1.4 取数步骤

定渠道APP/WMP/AMP
→
定归因EC/MDS/FC-
→
定Comp官方flag或手工窗口
→
取指标Sales/GC/User/Freq/AC
-- SQL骨架，仅用于提醒口径字段，日期/comp需按项目补齐 SELECT month, order_channel, if_ec, SUM(top_net_amount) AS sales, COUNT(DISTINCT CASE WHEN is_gc_count=1 THEN order_id END) AS gc, COUNT(DISTINCT mid) AS usercount, COUNT(DISTINCT CASE WHEN is_gc_count=1 THEN order_id END) * 1.0 / COUNT(DISTINCT mid) AS freq, SUM(top_net_amount) * 1.0 / COUNT(DISTINCT CASE WHEN is_gc_count=1 THEN order_id END) AS ac FROM hive.dws_order.t_order_pmix_for_analysis_d WHERE item_pmix_type IN ('Sold','Discount') AND order_channel IN ('New APP','Wechat MP','AliPay MP') GROUP BY 1,2,3;

档位标准判定备注

2.3 Heavy User与Sales关系怎么取

Heavy Sales = Heavy User × Heavy Freq × Heavy AC Heavy Sales Share = Heavy Sales ÷ Total Sales Heavy Contribution to ΔSales = ΔHeavy Sales ÷ ΔTotal Sales
-- Heavy生意拆解骨架 WITH heavy_base AS ( SELECT mid, user_seg FROM sandbox_cbi.ej_nre_xxx WHERE user_seg = '1-E-Heavy' ), orders AS ( SELECT mid, order_id, order_net_amount, is_gc_count, bi_dt FROM hive.ads_order.t_order_apply_d WHERE bi_dt BETWEEN '${start_dt}' AND '${end_dt}' ) SELECT COUNT(DISTINCT h.mid) AS heavy_user, COUNT(DISTINCT CASE WHEN o.is_gc_count=1 THEN o.order_id END) AS heavy_gc, SUM(o.order_net_amount) AS heavy_sales, COUNT(DISTINCT CASE WHEN o.is_gc_count=1 THEN o.order_id END) * 1.0 / COUNT(DISTINCT h.mid) AS heavy_freq, SUM(o.order_net_amount) * 1.0 / COUNT(DISTINCT CASE WHEN o.is_gc_count=1 THEN o.order_id END) AS heavy_ac FROM heavy_base h LEFT JOIN orders o ON h.mid=o.mid;
建议输出：Heavy User变化、Heavy Freq变化、Heavy AC变化，以及三者分别对Heavy Sales和Total Sales的贡献。这样能回答“Sales下跌是不是Heavy频次拖累”。

复用SQL前必查：高危口径陷阱

  • 3PO含不含JD：分析层3PO常含JD，但ej_order_ana底表is_3po只含MeiTuan/Eleme；BDB部分3PO也不含JD。
  • FC两种写法：order_type<>'MDS'与order_type='FC'并存，总量可能不同。
  • AC口径：AC=Sales/GC，人均销售=Sales/Usercount，不能混。
  • WD OR括号：历史08/10中我就喜欢码OR可能脱离日期/pmix约束，复用时必须重写括号。
  • DAU窗口：82-85品类下单用户日量中DAU匹配窗口只写单日，不能直接复用为长窗。
  • 留存窗口截断：b表窗口下界必须覆盖a全期+1天，否则cohort前段被截断。
  • BDB comp：多个文件comp为LEFT JOIN但未过滤，comp实际未生效。
  • 日期格式：bi_dt是yyyymmdd字符串，不能与带连字符日期串直接比较。
  • 标题不等于SQL：部分文件标题写APP但实际是WMP，或标题写FC但page_name是MDS。
  • 损坏/草稿文件：部分SQL存在字段缺失、全角符号、分号断链、空WITH等，不可直接执行。
建议：所有复用SQL都先过一遍“渠道、时间、comp、去重、分母、表粒度、优先级归因、黑产/EC处理”八项检查。
